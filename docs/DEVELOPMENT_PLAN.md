## 0. 本次重构的关键决策（先读）

### 0.1 产品一句话目标

开发一个**本地优先、无需开发者云端账号、可以不用 AI 完成大部分网申填写**的浏览器扩展：用户管理自己的结构化简历，插件识别当前招聘表单，在用户确认后填写；遇到未知字段时可由 AI 辅助解释，再将用户确认的字段定义和字段值保存到本机；记录本人已经申请过的职位并允许自行调整投递进度。

### 0.2 本版正式确认的原则

1. **两块浮层入口**：在用户打开插件时，于当前网页右上角出现悬浮面板，主标签仅包含「自动填充」「简历预览」；其他管理功能通过面板中的入口打开独立管理页。不得以只有 Chrome Side Panel 的形式替代右上角悬浮面板。
2. **预览中的三个操作必须可用**：「导航」定位简历分类；「刷新」读取当前本地资料；「编辑」进入可编辑的完整简历中心。导航、刷新、编辑绝不能做成装饰按钮。
3. **先有简历，才能填充**：首次启动优先引导新建本地档案（手动录入、空白档案、导入 PDF/DOCX）。AI 配置是可选步骤；没有 API、没有网络也能手动录入、扫描已授权表单、按规则填写和管理投递记录。
4. **自动填充默认不用 AI**：DOM 扫描、字段归一化、同义词匹配、已有映射记忆、日期/区号拆分、选项映射和表单写入校验均在本地完成。遇到歧义才允许用户主动选择 AI 辅助。
5. **未知字段的推荐模式是混合式**：先检测和提示；当用户主动填写完后，再提供「保存此字段及填写内容」的确认流程；AI 只负责解释/分类/候选建议，不能编造没有依据的个人信息。
6. **字段随时可增、可改、可删**：支持字段定义、字段值和重复经历实例分别管理，删除必须先预览影响，避免跨档案误删和旧值丢失。
7. **自动识别岗位信息，但不伪造投递成功**：识别公司、岗位、城市、职位链接等，可建立待确认记录；只有可靠成功信号加用户确认或用户主动标记，才记录为「已投递」。一键填表 ≠ 已投递。
8. **投递记录完全本地**：列表、看板、状态时间线、筛选、备注、JSON/CSV 导出；用户自行设置或修改申请状态。
9. **GitHub 只同步公共字段定义**：只允许字段键、名称、类型、分类、同义词、通用选项说明。**不上传字段值、不上传用户的站点映射和投递记录。**
10. **原始简历不保存**：PDF/DOCX 只用于临时解析和用户审校，入库仅保存确认后的结构化字段；不写入原始文件或永久附件缓存。
11. **凭据本地安全**：API Base URL 和模型配置本地保存；API Key 用用户口令派生密钥加密，解密明文不能进入网页内容脚本、日志、导出文件及公共仓库。
12. **不自动提交**：插件不能自动点击提交、确认投递、登录、支付、验证码、人机验证；文件上传也应由用户亲自完成或经过独立明确授权。

### 0.3 针对已有问题的直接结论

| 问题 | 结论 | 要求 |
|---|---|---|
| 自动填充一定要 AI 吗？ | **不需要** | 本地规则为主、AI 可选，禁用 AI 时仍能填写常见字段 |
| 不同字段名但内容相同怎么办？ | 同义词/语义上下文先匹配 | 如「院校 / 毕业学校 / University」可映射同一字段；「第一学历」不得误映射最高学历 |
| 未知字段先识别还是填完后保存？ | **两者结合** | 先提示未知；用户填完后主动确认保存字段和值，减少反复询问 |
| 年、月、日怎么自动填写？ | 按控件类型实现专门适配器 | `input[type=date]`、分离年月、日历弹窗、React/Vue 自定义选择器分别测试 |
| 为何 `+86` 被识别成字段？ | 控件语义和复合分组识别不足 | 国家区号属于手机号组件，不得作为独立简历字段 |
| 为何单独的「月」被识别？ | 丢失日期组件上下文 | 将「年」「月」「日」组合为一条日期字段，不创建三个未知简历字段 |
| 「同步更新在线简历」应保存吗？ | 通常是网站操作选项 | 应归类为站点操作型复选框，不进入个人简历字段库 |
| 填完即已投递吗？ | **不是** | 需要成功确认页、有效申请结果或用户主动确认 |

### 1.3 明确不做的事情

- 不建开发者运营的云端简历服务器，不收取会员费用，不设置本工具自行定义的每日填写次数。
- 不依赖 OfferLink 私有 API、数据库或前端资源，也不尝试复制其专有代码。
- 不保证适配互联网上所有招聘系统；每个复杂站点必须独立验证。
- 不自动投递、不代替用户作出求职意向和伦理敏感选择。
- 不把网页上的所有输入控件都当成简历字段。
- 不默认持续收集用户在任意网页上的输入；识别和学习均限定到用户授权的招聘表单。

## 2. 用户旅程和产品信息架构

### 2.1 首次使用流程（Onboarding）

```text
安装扩展 → 点击浏览器工具栏图标 → 右上角出现浮层
  ├─ 无本地档案：进入欢迎引导
  │   ├─ 手动创建档案（无需 AI）
  │   ├─ 上传 PDF / DOCX → 本地提取文本 → 用户逐项审校
  │   │   └─ 如选择 AI 结构化解析：先配置服务商 / API Key 并确认发送内容
  │   └─ 导入本地 JSON 备份
  ├─ 选择/命名当前档案，至少保存一项可用字段
  └─ 进入「自动填充」「简历预览」
```

- 欢迎页说明**不使用 AI 也能填表**；“跳过配置 AI”必须可点击。
- 已有档案但值为空：允许查看/编辑，但填充按钮应说明“暂无可填数据”，不能假报成功。
- 用户首次使用 AI 时，单独显示授权说明、数据预览和可选模型配置，不应在首次安装时强制要求 API Key。
- 多档案选择要保留到下次打开；不同档案值独立，不共享私有字段答案。

### 2.2 日常网申流程

```text
打开企业网申页面 → 点击插件图标 → 右上角浮层
  → 自动扫描已授权页面（必要时点击刷新）
  → 显示：可填写 / 需确认 / 资料缺失 / 不支持 / 操作控件
  → 用户预览每项映射及目标值
  → 点击「填写所选」或「一键填充」
  → 控件适配器写入 + 校验网页实际状态
  → 展示成功 / 失败及修复建议
  → 用户手动完成未识别字段
  → 点击「保存本次新增信息」→ 逐项确认新增字段和值
  → 用户自行检查网页并提交申请
  → 识别成功反馈或让用户确认状态 → 记录职位申请
```

## 3. AI 使用边界：必须写入产品与测试规范

### 3.1 功能决策矩阵

| 功能 | 不用 AI 是否可用 | AI 的角色 | 默认行为 |
|---|---|---|---|
| 手动添加/删除/修改字段及内容 | 是 | 不需要 | 本地完成 |
| 简历预览 / 导航 / 刷新 / 编辑 | 是 | 不需要 | 本地完成 |
| PDF/DOCX 文本提取 | 是（可提取文本的文档） | 可选用于语义结构化 | 优先本地解析；校对后保存 |
| 扫描版或图片简历 | 视本地 OCR 能力而定 | 可选视觉模型解析 | 明确告知需要视觉模型或本地 OCR，不偷传图片 |
| 招聘网页 DOM 字段扫描 | 是 | 不需要 | 本地扫描 |
| 已知字段同义词匹配 | 是 | 复杂歧义时可选 | 规则优先 |
| 年月日/下拉框/区号填写 | 是 | **不应用 AI 替代控件适配** | 本地专用适配器 |
| 未知字段含义判断 | 可用手动方式 | 可选辅助分类、候选映射和别名 | 用户点击后才调用 AI |
| 未知字段的个人值 | 是，用户输入 | 只能提出有证据支持的候选值，不能编造 | 用户确认值后保存 |
| 复用已确认映射 | 是 | 不需要 | 读取本地记忆 |
| 开放性问题 / 自我介绍草稿 | 手写可用 | 可选 AI 起草，逐条确认 | 不自动发布 |
| 岗位公司/名称/地点/链接识别 | 是 | 页面结构不清晰时可选辅助 | 本地规则 + 人工编辑 |
| 投递申请记录 / 状态 / CSV 导出 | 是 | 不需要 | 本地完成 |
| 公共字段定义导出与 GitHub 同步 | 是 | 可选推荐新别名 | 先脱敏审核再同步 |

### 3.2 严格的两种工作模式

**模式 A：仅本地（默认）**

- 不需要 API 配置；扫描、匹配、写入、查看资料、记录投递都可使用。
- 对所有“复杂未知字段”显示手动映射入口，但不阻断其余字段填写。
- 测试中必须验证关闭 AI 时，**不会调用任何模型服务端点**。

**模式 B：AI 辅助（用户显式开启）**

- AI 仅对用户选择的未知/歧义字段工作，支持批量选择；不能擅自扫描并发送整个网页。
- 每次发送前展示服务商、字段描述、选项和需要的上下文；必要时明确展示简历中将发送的最小片段。
- 模型调用可取消、可超时、可重试，记录耗时及请求量（不记录敏感原始内容）。
- AI 返回结构化建议，不直接执行 DOM 操作；所有变更仍由本地规则校验和用户确认。

### 3.3 典型场景

- 「毕业学校」「就读院校」「University」：若上下文明确，可本地合并匹配。
- 「最高学历院校」与「第一学历院校」：不能只凭字符串相似；需要教育经历层级和分组上下文，不确定时需要用户确认。
- 「是否接受岗位调剂」：如果本地无值，AI 只能建议它是布尔/单选字段，**不能猜测“是”**。
- 「可接受加班吗」：不自动填“是”；要求用户作出决定，存储为用户本地值。
- 网站出现「月」单字：先检查是否属于年月日组合控件；不是可独立新增的简历字段。

## 4. 右上角悬浮 UI：主要交互规范（参考截图，不复刻 OfferLink）

### 4.1 技术与布局

- 点击浏览器扩展图标时，在**当前标签页**注入/切换右上角悬浮面板，默认距右、距顶约 16–24 CSS px；避免被网页头部遮挡。
- 面板建议桌面宽度 380–460 px，高度上限 `min(78vh, 760px)`，内部滚动；用户可以拖动位置、折叠成小浮球、关闭并再次打开。
- 顶部区：产品名、当前档案、切换档案、设置、折叠/关闭。
- 主标签**只有两个**：「自动填充」「简历预览」。岗位跟踪以快捷卡片/入口呈现，完整管理页单独打开。
- 使用 Shadow DOM 或等效样式隔离，避免招聘网页 CSS 影响插件；样式及脚本作为 MV3 打包资源。
- 支持键盘导航、焦点管理、Escape 关闭浮层、可访问性标签；禁止遮挡网页最终提交操作。
- 面板 z-index 需可控且可恢复，不依赖无限增大；支持站点自定义避免遮挡区域。
- 默认不在任意网页自动浮出、持续监听输入。用户打开/授权后才激活当前站点表单能力。

### 4.2 「自动填充」主标签布局

```text
┌─ localapply-ai   [当前档案 v]  [设置] [×] ───────┐
│ [ 自动填充 ]             [ 简历预览 ]             │
├──────────────────────────────────────────────────┤
│ 当前页面：XXX 招聘   [刷新检测] [AI 辅助：关闭]   │
│ 检测结果：可填写 12 / 待确认 2 / 缺资料 3 / 排除 2 │
│ ┌──────────────────────────────────────────────┐ │
│ │ 姓名              → 基本信息/姓名       ✓  │ │
│ │ 最高学历学校      → 教育经历(硕士)/学校  ✓  │ │
│ │ 第一学历学校      → 待确认              !  │ │
│ │ 手机国家区号 +86  → 电话组件的一部分    —  │ │
│ └──────────────────────────────────────────────┘ │
│ [只看未知字段] [保存本次新增信息]                │
│ [填写所选字段]               [一键填充此页]       │
│ 填写结果：11 成功 / 1 失败 [诊断]                │
│ 岗位信息：已识别/待确认       [添加申请记录]       │
└──────────────────────────────────────────────────┘
```

- 「重新检测」只扫描最新 DOM，不清空简历字段值或历史规则。
- 每条字段展示：原网页名称、内部字段、值的脱敏预览、信心等级、控件类型、写入状态。
- 可选择“本地匹配”“AI 辅助”“手动选择本地字段/经历”；AI 按钮只对选中的未知字段调用。
- 显示排除项计数与理由（如 `+86` 区号、验证码、页面操作按钮）；排除项默认折叠，不污染主列表。
- 一键填充前预览将被覆盖的网页现有值；默认**不覆盖非空且与本地不同的字段**，用户可逐项允许。

### 4.3 「简历预览」主标签布局

```text
┌─ localapply-ai   [当前档案 v]  [设置] [×] ───────┐
│ [ 自动填充 ]             [ 简历预览 ]             │
├──────────────────────────────────────────────────┤
│ 我的简历 · [导航 v]      [刷新]       [编辑]      │
│ 提示：单击复制字段，或先选中网页目标再点击填入    │
│ 个人信息：姓名 / 电话 / 邮箱 / 地址…              │
│ 求职意向：岗位 / 城市 / 到岗时间…                 │
│ 教育背景：本科 [展开] / 硕士 [展开]                │
│ 实习经历：第一段 [展开] / 第二段 [展开]            │
│ 项目经历：第一项 [展开] / 第二项 [展开]            │
│ 技能语言 / 证书荣誉 / 自我评价 / 自定义字段        │
└──────────────────────────────────────────────────┘
```

三个操作定义必须明确：

1. **导航**：按分类快捷跳转；支持搜索字段/项目；滚动到目标位置并高亮。不得只是空下拉。
2. **刷新**：重新读取 `chrome.storage.local`/IndexedDB 的当前档案并重渲染；保存中的修改需要先处理冲突，不得覆盖未保存的编辑。
3. **编辑**：打开完整简历中心（扩展内部页面），定位当前档案或分组；支持添加/删除字段、重复经历增减和结构化编辑。

可选扩展：单击字段“复制到剪贴板”；当用户在网页上主动选定一个输入控件后，允许通过“将此值填入选中控件”操作，不自动向所有焦点发送敏感信息。

### 4.4 独立管理页布局

- 左侧导航：概览 / 简历中心 / 字段库 / 投递记录 / AI 设置 / 数据备份 / 调试与关于。
- 简历中心：左侧分组导航、右侧分组表单，重复经历使用独立卡片和「+ 添加经历」。
- 投递管理：列表视图 + 看板视图，可切换状态、编辑备注、时间线和导出。
- 设置页：清楚显示“仅本地模式 / AI 辅助模式”、当前模型服务商、密钥是否解锁。
- 设计语汇：简洁中性色底、少量蓝色用于操作强调；状态语义使用颜色+文字+图标，不仅靠颜色区分。与 OfferLink **功能参考一致但视觉独立**。

## 5. 可增删的简历字段体系（参考 OfferLink 分类）

### 5.1 默认分组与建议字段

以下为**建议默认集合**，不是强制固定清单，所有分类允许用户新增字段；在适当权限下可隐藏、禁用或删除用户自定义字段。

| 分组 | 建议内置字段与注意点 | 重复结构 |
|---|---|---|
| 个人信息 | 姓名、姓名拼音、性别、出生年月、电话、邮箱、现居城市、详细地址、证件类型/号码（敏感）、政治面貌 | 一般单组 |
| 求职意向 | 目标岗位、意向行业、城市、期望薪资、到岗时间、工作性质、是否接受调剂 | 可以多份意向 |
| 教育背景 | 学校、校区、学历、学位、专业、入学/毕业年月、GPA/排名、学位类别 | **多段，需稳定 recordId** |
| 实习经历 | 公司、部门、岗位、起止年月、职责、成果 | 多段 |
| 工作经历 | 公司、岗位、起止日期、工作性质、职责、离职原因（可选） | 多段 |
| 项目经历 | 项目名、起止日期、角色、工作描述、技术栈、成果 | 多段 |
| 语言能力 | 语种、水平/等级、成绩、听说读写能力、考试日期 | 多项 |
| 证书与资质 | 证书名称、颁发机构、日期、编号（可能敏感） | 多项 |
| 获奖经历 | 奖项、获奖级别、日期、说明 | 多项 |
| 技能专长 | 语言、框架、工具、技能等级、描述 | 多项或标签 |
| 自我描述 | 自我评价、优势、求职动机、个人介绍 | 可支持不同版本 |
| 家庭/社会关系 | 家庭成员、姓名、关系、工作单位等（高敏感） | 可选、严格授权 |
| 自定义字段 | 由用户或 AI 建议的其他字段，如“是否接受调剂” | 自定义类型决定 |

### 5.2 字段的三个层级

- **FieldDefinition（字段定义）**：字段“是什么”，如 `birth_date`、`出生日期`、`date`、别名、分组。可进入经审核的 GitHub 公共字段库，但不含值。
- **ProfileFieldValue（个人值）**：当前档案“填什么”，如具体出生日期或答案。始终保存在个人本机，默认不进入公共仓库。
- **FormMapping（网页映射）**：某网站的某类控件对应哪个内部字段/经历实例，仅本地保存；最新产品要求不将网站映射同步到 GitHub。

不得在公开字段定义内加入 `value`、`answer`、`examplePersonalValue`、联系方式或真实用户原文。

### 5.3 添加、编辑、删除和重复经历

- 新增字段：输入名称、类型、分类、可选项与别名；建议用户提供稳定 key，系统生成不冲突 ID。
- 修改字段定义：旧 fieldId 稳定不变，别名改动不能导致原有值断开；类型变化要预览转换风险。
- 删除用户自定义字段：显示其在几个档案被使用、是否存在网页映射和多少个值；提供“仅从当前档案删除值”“停用字段”“彻底删除字段及关联值”等不同操作。
- 公共内置字段建议默认仅隐藏/停用，不随单人操作从公共库全局删除。
- 删除一段教育/实习经历时按 `recordId` 处理，不以数组序号作为长期主键；列表重排不影响映射。
- 多次导入同一简历，使用标准化标识+内容指纹辅助去重；不因时间或文本细微差异误合并不同经历。
- 空字段可隐藏，但在“显示全部字段”下应可见并编辑；字段值可以清空、恢复备份、查看来源。

### 5.4 默认格式标准化

- 日期统一内部格式：`YYYY-MM-DD` 或 `YYYY-MM`，另有精度 `day | month | year`；展示可为 `2026年10月`，但不混淆内部值。
- 电话保存国码、地区号与本地号码的结构化表示或统一 E.164 兼容表示，展示层脱敏；填表时根据目标组件拆分。
- 单选/布尔字段保存标准值与显示标签的映射，不把用户选择的选项索引当作永远不变的答案。
- 地址保留省、市、区和详细地址的可选结构；不同网站需能分级选择。
- 期望薪资保留金额、单位、周期、币种，不能把“年薪 18 万”盲填为“月薪 18 万”。

## 6. 网申网页扫描引擎：先区分“字段”与“控件”

### 6.1 不要扫描到一个可交互元素就认作字段

建议将网页节点先归为以下类型：

1. `data_field`：需要从个人档案填写的字段，例如姓名、学校、开始日期。
2. `compound_part`：某个字段的子控件，如 `+86` 国家区号、日期中的“月”、分级地址的“市”。
3. `site_action`：网站行为选项，如“同步更新在线简历”“确认已阅读”“复制简历内容”，不属于个人档案。
4. `security_control`：密码、验证码、短信验证码、人机验证、支付信息等，一律不采集、不填写。
5. `navigation_control`：下一步、上一步、保存草稿、提交投递、查看详情等按钮，绝不进行字段入库。
6. `display_only`：纯文本、说明、字段标题、进度标签，不应被作为用户输入。
7. `unknown_control`：无法安全归类的特殊控件，展示待核对并允许人工报告。

**先分类，再解析字段含义；先建立组件分组，再生成候选字段。** 不能只对全部 `input`、`select`、`textarea` 逐个打标签。

### 6.2 DOM 扫描步骤

```text
[用户授权扫描当前标签页]
  → 判断网页是否存在有意义的申请表单
  → 排除登录页、验证码区、密码区及插件自己的 Shadow DOM
  → 构建节点结构和视觉/语义分组
  → 提取 label / for / aria-labelledby / aria-label / name / placeholder
  → 读取当前可见表单块的标题与上下文
  → 识别复合组件：电话、日期、地址、量表、动态经历
  → 判断 data_field / compound_part / site_action / security_control
  → 对 data_field 计算稳定的局部控件指纹
  → 映射内部字段 / 显示待确认 / 排除并说明原因
```

字段标签优先级建议：显式 `<label for>` > `aria-labelledby` > 同一组件的标签和 form-item 名称 > `aria-label` > 周围结构标题 > `name` > `placeholder`；placeholder 仅作弱证据。

### 6.3 同名字段与重复经历

- 网页中出现多个“开始时间”时，必须依据所在“本科教育 / 硕士教育 / 第 1 段实习 / 项目经历”分组定位。
- 先识别重复组标题与“新增经历”容器，再映射到具有稳定 `recordId` 的本地经历；用户可手动调整配对顺序。
- 避免只依靠 `nth-child` 或绝对 XPath：页面插入新经历后会移位；优先语义标签、分组标题、局部结构和可见性。
- 跨页表单、SPA 路由变更、动态展开后应重新扫描**变化的区域**，以版本指纹去重，不反复添加相同候选。

### 6.4 国家区号 `+86` 特别处理

**已知错误场景**：手机号栏前的 `+86`、国家区号下拉被误当成“未知字段”。

建议采用：

- 识别号码输入与国码选择器的共同容器（电话字段的 label、国家选择按钮、国家名称、+86、电话号码输入）。
- 建立一个 `phone_number` 语义字段，内部可维护 `countryCode`、`nationalNumber`；区号视为同一复合字段的子控件。
- 用户有 `+86` 的国内号码时，自动适配“国码下拉 + 11 位号码”的组合；不得同时将 `+86` 和 `+86xxxxxxxxxxx` 复制到两个位置造成重复。
- 遇到特殊电话号码或国际号码不能凭空假设 `+86`；区号候选列表中须按国家/区号精确匹配。
- `+86` 的存在只是组件特征，不是一个需要用户单独新建到公共简历字段库的字段。
- 对原仓库已经实现的电话区号识别逻辑先做回归测试；复现失败原因后优先修复原适配器。

### 6.5 需要排除的典型控件

| 网页控件 | 类型 | 应如何处理 |
|---|---|---|
| `+86` 国码按钮 | `compound_part` | 归入手机号组件，必要时填写国家代码 |
| `年` / `月` / `日` | `compound_part` | 合并成一个对应日期字段 |
| “同步更新在线简历” | `site_action` | 由用户自行选择；不加入个人档案字段库 |
| “发送验证码” | `security_control` / `navigation_control` | 跳过、不点击 |
| “我已阅读并同意” | 网站协议确认 | 跳过；不得替用户默认勾选 |
| “保存草稿”“下一步” | `navigation_control` | 不当成字段；不自动点击 |
| 岗位地点展示标签 | `display_only` | 可用于识别职位元信息，但不作为简历字段 |
| 表格行内“删除此经历” | `navigation_control` | 不执行；仅可用于识别重复组边界 |

### 6.6 复杂 DOM 的支持边界

- 原生 DOM + 开放的 Shadow DOM：可支持，需谨慎递归并防止扫描插件自身。
- 同源 iframe：在授权条件下可支持，避免多帧重复填充；跨源 iframe 需要额外 host permission，无法授权时显示原因。
- closed Shadow DOM、浏览器安全页面、无权限跨域嵌入：不承诺自动识别，提供手工复制或诊断建议。
- Canvas 绘制的特殊输入框：原则上不支持普通 DOM 扫描；不默认启用屏幕 OCR 或模拟图像点击。

## 7. 日期、月份、时间区间与地区选择器专项

### 7.1 日期填写为什么会失败

常见原因不只是“文字没有填进去”，还包括：

- 网页使用 `input[type="date"]`，直接填 `2026年10月25日` 不符合原生格式。
- 页面拆成三个选择器“年 / 月 / 日”，原匹配算法将“月”当成独立未知字段。
- React/Vue/Ant Design/Element Plus 组件必须触发其状态更新，单纯设置 DOM `.value` 可能无效。
- 日期选择器存在浮层、候选月份、可选范围、跨月按钮，手动写入只更新可见文本，不更新组件内部值。
- 入学/毕业时间可能只需要 `YYYY-MM`，某些控件强制要求日，不能无依据地静默填成 1 日。

### 7.2 DateAdapter 设计

开发统一接口（名称可根据项目结构调整）：

```ts
interface DateValue {
  year: number;
  month?: number;
  day?: number;
  precision: 'year' | 'month' | 'day';
}

interface DateAdapter {
  canHandle(target: Element): boolean;
  fill(target: Element, value: DateValue): Promise<FillResult>;
  verify(target: Element, value: DateValue): Promise<boolean>;
}
```

按实现优先级拆分：

1. 原生 `date`、`month`、`datetime-local`。
2. 单输入框自由文本日期（依其格式提示转换为 `YYYY/MM/DD`、`YYYY-MM` 等）。
3. 年月分离 `select` / 输入框（严格绑定同一日期语义组）。
4. 省市区/起止时间采用复合组件适配器，不混入普通文本匹配。
5. 常见自定义日期弹层（日历年/月选择、月份网格、起止日期范围）。
6. 北森/Moka/飞书等实际站点提供更具体的适配层，而不是让 AI 猜如何点击。

### 7.3 验证与失败反馈

- 验证实际组件显示值、输入事件后的受控状态和网页校验提示；必要时通过失焦后再读取复核。
- 无法判断月/日精度或可选范围时显示“需要用户确认”；不得随便选择今天或 1 日。
- 必须覆盖跨年份、闰年、2 月、缺失日期、仅年月和日期范围等测试。
- 对日期禁止将某一个组件分割出来的“月”写入公共字段库。

### 7.4 其他复合控件

- 地址选择器：省→市→区异步级联，每级选择后等待选项加载。
- 单选/多选：根据真实候选文案和规范值匹配，避免序号变化导致错选。
- 手机号区号：国家码 + 本地号码分离填入；验证码和短信发送按钮排除。
- 薪资：同时识别单位、周期、范围（例如年薪/月薪、税前/税后），不一致时停止自动填充。

## 8. 字段匹配与未知字段学习：采用混合方案

### 8.1 FieldMatchingEngine 匹配顺序

```text
同网站 + 同字段结构 + 用户确认过的映射
    ↓ 未命中
字段 ID / 标准标签 / 已知别名
    ↓ 未命中
上下文规则（学历层级、经历组、岗位/个人资料区别）
    ↓ 未命中或仍有歧义
人工选择已有字段 或 用户主动启用 AI 建议
    ↓
逐项确认，写入目标控件，验证成功
    ↓
记录本地映射（不上传 GitHub）
```

不得使用未经校准的“AI 自报 95% 置信度”作为自动写入依据。置信度是提示数据，应综合规则可信度、字段敏感度、目标已有值、分组和候选唯一性。

### 8.2 为什么推荐“先发现 + 后学习”

只在填前要求手动创建字段：打断用户完成投递，而且用户不一定知道填写的最佳内容；只在填后偷偷读取：违反最小化原则、容易把账号、验证码、网页操作控件采集进资料库。

**推荐交互：**

1. 打开本页后显示“检测到 3 个未知字段”。
2. 用户可选择“AI 解释”“映射到已有字段”或“稍后自己填写”。
3. 用户在网页上照常填写；插件只在用户授权的本页、指定表单范围内暂存候选变化。
4. 用户主动点击“保存本次新增信息”；界面预览：网页字段标签、填写内容、建议字段名/分类、是否属于个人档案。
5. 用户逐项选择“保存为新字段 / 保存到已有字段 / 仅记住网页映射 / 忽略”，确认后持久化。
6. 下一次打开同类网申字段时使用本地已确认资料自动匹配，无需再调用 AI。

### 8.3 手填后候选值的采集边界

- **默认关闭**自动保存；可以允许当前标签页开启“检测新字段填写变化”，但监听只生成**内存中的待确认候选**，不直接写永久数据库。
- 对 `input/change/blur` 变化进行去抖、去重，必要时结合 `MutationObserver` 监测新出现的表单；避免每击键产生数据库写入。
- 不依赖 `event.isTrusted` 单独判断人工输入，配合插件自己的写入事务标记、防重复记录和数据差异校验。
- 页面关闭、用户取消或超过会话生命周期后，未保存的候选及时释放；不能形成隐藏历史记录。
- 明确过滤密码、短信验证码、支付卡号、网页登录信息、协议复选框、无关搜索框和浏览器内其他网站内容。
- 身份证、住址、家庭成员等敏感值如需保存须额外确认，并确保不会用于公共字段同步。
- 对已经存在的本地值，如果网页出现不同内容，提供合并/替换/仅此页保留的选择，不能静默覆盖原档案。

### 8.4 新字段存储状态机

```text
unknown → suggested → awaiting_user_value → pending_confirmation
        ↘ mapped_existing_field ↗             ↓
                                               confirmed → active
                                                    ↓
                                                 disabled / deleted
```

要区分**字段定义存在但缺少值**和**字段定义本身不存在**。缺少值不得由 AI 编造；字段定义存在时原则上不重复建立新字段。

### 8.5 本地映射记忆及纠错

- 记忆键由站点域名 + 表单区域 + 字段语义/标签 + 相对结构特征组成，不直接持久化含个人值的完整 DOM。
- 存储 `fieldId` 和重复经历 `recordId`，不依赖数组下标。
- 保存本次匹配结果的来源、用户确认、验证时间、成功/失败计数，允许关闭不可靠规则。
- 用户手动纠正错填后提供“记住这次修正”；同一站点相同字段下次优先使用修正规则。
- 当网站结构改变或新规则冲突时，不强行复用旧规则；提示“需要重新确认”。

### 8.6 AI 识别建议的格式

AI 输出只允许明确的有限动作：

- `map_existing_field`：关联已有 `fieldId`/`recordId`。
- `create_field_definition`：建议新的字段定义；实际值仍由本地资料证据或用户手动提供。
- `skip_non_resume_control`：建议忽略页面操作控件。
- `needs_user_choice`：不能确定时标记为待用户选择。

所有输出需通过 JSON Schema 验证；字段 ID 必须在白名单中校验或由本地生成；任何模型输出的脚本、XPath 可执行片段、任意网页点击命令或新的 API URL 都不得执行。

## 9. 岗位识别和投递记录：单独的完整功能模块

### 9.1 目标

用户进入职位页面后，插件能识别职位基础信息，并在用户确认后新增或更新投递记录。提供 OfferLink 截图展示的“申请追踪 / 当前申请详情 / 求职工作台”类体验，但界面与文案独立设计。

### 9.2 岗位信息识别策略（不依赖 AI）

优先从以下位置提取候选：

1. 网站提供的 JobPosting JSON-LD / 结构化数据（先校验来源可信性）。
2. 职位详情区的标题、公司名、地点、职位性质、JD 区块。
3. 页面标题、URL 路径和网站适配器识别的职位 ID。
4. 用户手动指定或编辑信息，作为最终确认依据。
5. AI 可选：当网页语义杂乱、规则无法区分广告或页面标题时，仅对用户选定的职位描述片段辅助抽取。

待保存字段：公司、职位名称、招聘平台、职位 ID（如能识别）、原职位 URL、工作地点、职位类型、投递日期/记录创建时间、职位摘要、当前状态、备注、更新历史。不要把网页导航菜单/推荐职位误记为当前投递岗位。

### 9.3 申请状态定义

用户默认可选状态：

- `saved`：已收藏 / 准备投递。
- `draft`：正在填写 / 尚未提交。
- `applied`：已投递。
- `screening`：筛选中 / 筛选通过（可扩展）。
- `assessment`：测评 / 笔试。
- `interview`：面试中。
- `offer`：收到 Offer。
- `rejected`：未通过。
- `closed`：结束 / 撤回。

支持更改状态、时间戳、备注及自定义标签，不能只显示固定看板列。默认允许状态手动设置，后续可以增加自定义流程配置。

### 9.4 什么时候可以认定“已投递”

| 页面事件 | 可执行操作 | 是否自动认定已投递 |
|---|---|---|
| 用户打开职位详情 | 提取岗位候选，建议收藏 | 否 |
| 用户完成一键填充 | 生成草稿记录，等待提交 | 否 |
| 用户手动点击网页提交 | 标记“提交结果待确认”，观察后续反馈 | 否，点击不等于成功 |
| 页面出现可信申请成功提示或申请编号 | 弹出“检测到投递成功，是否记录？” | 经用户确认后可以 |
| 页面报错 / 身份认证失败 | 保持草稿或待确认 | 否 |
| 用户在插件手动选择“已投递” | 按用户明确操作更新 | 是 |

同一职位避免重复计数。去重键优先“站点 + 职位稳定 ID”，回退为规范化 URL + 公司 + 岗位名，出现岗位重发布时允许用户选择“新一轮投递”。

### 9.5 申请记录的页面设计

**面板快捷入口**：当前岗位候选、上次操作日期、是否已经记录、打开投递管理。主面板仍保持两个标签，不增设第三个主标签。

**管理页**：

- 列表/看板视图切换，状态列可以展开或隐藏。
- 搜索：公司名、岗位名、地点、备注。
- 筛选：状态、申请日期、招聘平台、岗位类型、城市。
- 点击卡片显示侧边详情：岗位基本信息、职位链接、已保存的职位摘要、申请时间线、待办事项和备注。
- 支持新增、编辑、删除、归档及批量导出。
- 状态更新明确写入历史，如 `2026-10-25 已投递 → 2026-10-28 测评`；此类日期为示例。

### 9.6 导出格式

- CSV：UTF-8 BOM，保证 Windows Excel 中文可读；含公司、岗位、地点、平台、网址、状态、申请日期、最近更新、备注。
- JSON：包含完整 ApplicationRecord、状态事件、`schemaVersion`，可重新导入并去重。
- CSV/JSON 默认不含 API Key、个人简历正文；如职位摘要含个人备注，应在导出前明确提示用户。
- 增加导出预览和日期/状态筛选，不强迫导出所有记录。

## 10. 数据模型与存储规则

**注意：以下是目标领域模型，不应绕开已有 Schema v3 强行替换。Codex 必须先检视阶段 2 的实际数据，采用迁移适配层或必要的 Schema v4。**

### 10.1 公共字段定义（严格无值）

```json
{
  "schemaVersion": 1,
  "fieldId": "career.accept_relocation",
  "label": "是否接受工作地点调剂",
  "type": "boolean",
  "group": "career_preference",
  "aliases": ["是否服从工作地点分配", "是否接受全国调剂"],
  "options": [
    { "key": "yes", "label": "是" },
    { "key": "no", "label": "否" }
  ],
  "description": "由应聘者本人决定是否接受工作地点调整"
```

### 10.2 个人字段值（仅本地）

```json

  "source": "user_confirmed",

```

`recordId` 用于重复经历；字段值可以是文本、日期、布尔、数组或经验证的结构化类型。重复项目不可复用相同 `recordId`。

### 10.3 网站映射记忆（仅本地）

```json

```

这属于用户自己的网页规则，**不属于 GitHub 公共字段同步范围**。

### 10.4 未知字段待确认候选（默认仅会话内存）

```json
{
  "candidateId": "candidate_001",
```

不将实际候选值写入公共字段定义；临时缓存原则上保留到当前页面会话结束或用户主动取消，敏感字段需要二次确认。

### 10.6 存储边界

| 存储域 | 保存内容 | 安全约束 |
|---|---|---|
| `chrome.storage.local` | 档案索引、结构化字段、设置、状态 | 不视为加密存储；通过访问级别限制内容脚本读取 |
| IndexedDB（可选） | 大型结构化记录、投递历史、字段映射 | 支持版本升级和事务回滚 |
| `chrome.storage.session` | 临时解锁态、短期会话标记 | 不当作永久备份，不跨重启保证存在 |
| 后台短期内存 | 文件解析、未确认的手填候选 | 用后释放，禁止持久化原始简历文件 |
| GitHub 仓库 `data/fields/` | 审核后的公共字段定义 | 绝不含个人字段值、个人网站映射、投递记录、API Key |

### 10.7 API Key 加密与模型设置

- 延续阶段 2 已有口令加密机制；确认 AES-GCM 或同级加密实现具有随机盐、随机 IV、密钥派生和错误处理。
- 口令不得与密文一起写入磁盘；“记住配置”与“保持解锁”是两个不同选项。
- 锁定状态下仍允许普通本地自动填充；需 AI 时提示解锁。
- 允许配置多个模型服务商并切换，包括自定义 OpenAI 兼容端点；模型超时、API 配额、网络错误均需友好反馈。
- API 请求从 Service Worker/受控后台发起，所有消息参数和发起 tab ID 校验；不要在网页环境中暴露密钥。
- API Base URL 必须校验 HTTPS、合法主机及域名权限；本地测试用 Mock 服务需显式的开发模式隔离。

### 11.4 权限与 MV3 设计

- 优先 `activeTab` + `scripting`，由用户点击图标授权当前标签页；若需要在常用招聘站点自动提醒，可在用户明确授权后追加**可选**站点权限。
- 模型服务商的 `host_permissions` 根据用户选择按需申请。禁止为了便利默认无限制访问所有网站。
- 背景与内容脚本通过受控消息协议通信，验证发送者、tab、origin、允许动作；不允许网页直接请求读取完整档案和明文 API Key。
- 使用 MV3 打包脚本，不下载远程 JS 直接执行；远程字段 JSON 只作数据，必须校验 schema。
- Content Script 在隔离环境运行；不得运行模型建议的任意脚本。对 Shadow DOM 和网站事件兼容做好最小权限设计。

## 14. 数据隐私、可用性与失败策略

### 14.1 数据流安全检查

1. 只有用户触发的 AI 请求可以向第三方模型服务发必要信息；发送前明确显示将发送的内容和目的。
2. 表单扫描默认只在用户授权页面发生；`activeTab`、可选站点授权和导航场景的边界需测试。
3. 网页内容视为不可信输入，防提示词注入、XSS、无关链接及假字段诱导；AI 不能控制安全决策。
4. 扩展 UI 与网页隔离；模型服务和仓库字段 JSON 必须做结构验证与文本安全渲染。
5. 手机、证件、住址、家庭成员等高敏感值在面板中默认遮挡，填入前做二次确认（可逐站点记忆用户选择，但不得绕过安全规则）。
6. 文件解析时处理 MIME/大小、PDF/DOCX 格式检查、异常内容和超时；不要永久保存原始文件或完整原始文本。
7. 本地资料的 JSON 备份是用户主动导出，独立于公开字段同步；提醒用户备份文件包含真实个人信息，应妥善保存。
8. 扩展卸载一般会丢失扩展本地数据，用户应能主动导出并恢复；不可承诺浏览器缓存永久可靠。

### 14.2 异常与降级策略

| 异常 | 应对 |
|---|---|
| 没有简历 | 跳到新建档案引导，不假装填写成功 |
| 没有 API Key / Key 未解锁 | 无 AI 的流程继续可用，AI 按钮提示配置/解锁 |
| 模型超时/限流/错误 | 显示可重试信息，保留本地映射与待确认状态 |
| 网站无权限 | 提示点击授权或手动操作，不绕过浏览器权限 |
| 自定义控件写入失败 | 保留原值，显示具体失败控件与人工操作建议 |
| 网站 DOM 重新渲染 | 重新定位控件并复核，避免针对已卸载节点写入 |
| 重复字段冲突 | 不无声覆盖，提供映射候选和选择 |
| 备份导入失败 | 先校验和创建回滚点，失败不改变现有资料 |
| GitHub 同步失败 | 待同步队列保留，公共字段库不污染，本地使用不受影响 |
| 岗位自动识别不完整 | 提供手动编辑；不能把错误岗位自动加入已投递 |

### 14.3 非功能质量目标

- 浮层在不同网页打开不出现明显卡顿，内容脚本避免全局高频扫描；优先局部增量扫描。
- 每次扫描提供可取消与错误反馈，动态 DOM 变化避免无限循环、重复保存、过量内存占用。
- 关键操作（创建字段、覆盖值、删除、导入、应用规则、状态更新）都有确认、撤销或可回滚路径。
- Chrome/Edge 的升级、MV3 Service Worker 休眠/唤醒、离线/恢复联网均需测试。
- 安全与数据完整性优先级高于“自动填充率”“点击次数”或 UI 动画。

## 15. Codex 开发过程标准

### 15.1 每个阶段的固定流程

```text
读取 DEVELOPMENT_PLAN.md / DEVELOPMENT_PROGRESS.md
    ↓
核对当前代码、数据 Schema 与回归测试命令
    ↓
列出本阶段任务 ID、预期改动文件、验收用例
    ↓
逐项实际编码（不要只给设计）
    ↓
单元测试 → 集成测试 → Playwright E2E → 失败修复
    ↓
核对 API/隐私/未知字段/日期/手机控件的负向用例
    ↓
更新 DEVELOPMENT_PROGRESS.md：结果、证据、未解决问题
    ↓
总结并停止，等待用户批准下阶段
```

### 15.2 Git 工作流要求

- 本项目直接使用用户自己的 `origin/main`，不要求 `upstream`，不自动创建 `dev` 分支。
- Codex 修改前可记录当前提交号，建议分功能提交以便回滚；**未经用户明确许可不得 `git push`、不得创建 PR、更不得自动发布扩展**。
- 保持 `.gitignore` 完整：密钥、真实简历、用户备份、浏览器测试 profile、原始附件、含私有信息的截图和日志均不得提交。
- 公共字段同步属于阶段 7 的独立功能，**不意味着其他开发阶段可以自动提交个人档案**。

### 15.3 交付报告格式

每一阶段结束输出：

1. 阶段编号与完成时间（本机时间）。
2. 实现的功能、任务 ID 和文件列表。
3. 改动的数据结构、迁移路径、回退方法。
4. 实际执行的命令以及单元/集成/Playwright 通过和失败数量。
5. 可复核的测试截图/日志/报告路径（必须脱敏）。
6. 仍未解决的问题、风险和未测真实网站。
7. 是否满足阶段出口验收（逐条说明，不能笼统说完成）。
8. 进度文档更新位置和下一阶段建议。

### 15.4 严禁的“伪完成”

- 只创建 JSX/HTML 静态界面就宣称 AI 学习或网申自动填写完成。
- 只给字段贴“已填写”状态，但不读取真实网页值验证。
- 只识别 submit 按钮就把岗位写成“已投递”。
- 只靠模拟网页就声称兼容所有北森/Moka/飞书网站。
- 将问题严重程度降低或删除失败测试，让通过率好看。
- AI API 未测试就宣称支持所有服务商；真实模型需另行授权小规模抽检。
