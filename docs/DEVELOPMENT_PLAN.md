## 1. 项目概述

### 1.1 产品定位

开发一款 **本地优先、用户自主配置大模型 API、能够持续学习新字段的 Chrome / Edge 网申自动填写扩展**。目标工作流为：

**上传简历 → 本地提取 / AI 解析 → 用户核对 → 保存结构化资料 → 扫描招聘表单 → 本地优先匹配 → AI 处理疑难字段 → 用户确认 → 一键填写并校验 → 记住映射。**

### 1.2 不可妥协的产品原则

1. **资料归用户所有。** 不需要开发者账号、云端数据库或会员系统；普通填表不设置每日次数限制。
2. **原始简历不留存。** 支持临时上传 PDF/DOCX，保存结构化解析结果；不将原始文件、图片或完整原文写入持久化数据库及备份。
3. **个人字段值只在本机。** 用户的姓名、院校、经历、字段回答及模型 API Key 不同步到 GitHub。
4. **公共字段与字段内容分离。** GitHub 只接收经过审核的**字段定义**（ID、名称、类型、分类、同义词、必要的通用选项定义），**绝不接收用户填写的字段值**。网站专属个人映射默认也不上传。
5. **规则优先，AI 兜底。** 已知字段尽量本地匹配；未知字段才由用户主动触发 AI。API 费用和服务商数据处理规则由用户自行掌握。
6. **人始终负责确认。** 新字段、新值、修改旧值、敏感字段填写、外部同步均需明确授权；不自动提交投递、不填写密码或验证码。
7. **可验证、可回滚。** 每个阶段必须有自动化测试、手工验收项、错误日志和明确的回退策略。
8. **保留开源合规信息。** 保留原仓库 MIT LICENSE、必要的版权声明与第三方依赖许可。

### 1.3 范围与非目标

**范围内：** 多简历档案、PDF/DOCX 解析、本地字段库、AI 字段识别、通用表单填写、复杂控件适配、字段记忆、公共字段定义 GitHub 同步、数据备份、中文 UI、测试与发布。

**当前不追求：** 自动登录、验证码绕过、自动投递、无授权批量申请、云端储存个人简历、任何招聘网站 100% 兼容、自动将用户简历值汇总到公共仓库。

## 3. 目标架构与模块边界

### 3.1 核心模块

| 模块 | 职责 | 边界要求 |
|---|---|---|
| UI（Side Panel / Options） | 中文页面、资料编辑、AI 授权、差异预览、同步中心 | 不直接操作第三方网页 DOM，不直接暴露密钥 |
| Content Script / Field Scanner | 扫描当前授权页面的字段标签、类型、分组及选项 | 只提取必要元数据；不直接读取全部本地个人资料 |
| Rule Matcher | 字段别名、学历层级、重复分组、本地已确认映射 | 能离线运行；输出候选及原因 |
| AI Orchestrator | 组装脱敏请求、模型调用、JSON 解析与校验 | 仅扩展可信上下文调用；AI 输出只当数据，不当指令 |
| Field Proposal Service | 新字段定义建议、已有值关联建议、确认后新增 | **定义和值是两次独立写入操作** |
| Autofill Adapter | 输入框、下拉框、日期、React/Vue、动态经历填写 | 写入后校验实际状态；不提交申请 |
| Local Repository | Schema、用户档案、规则记忆、备份与迁移 | 原文件不入库；数据变更需可回滚 |
| Public Catalog Sync | 公共字段定义导出、审核、GitHub 同步及更新合并 | 白名单输出；永不读取个人字段值 |
| Diagnostics / Tests | 脱敏日志、模拟站点、Mock AI、E2E、版本回归 | 使用虚构资料；不记录密钥或真实简历 |

### 3.3 四种核心数据对象

```ts
interface FieldDefinition {
  id: string;                 // 稳定唯一 ID，例如 accept_relocation
  label: string;              // 是否接受工作地点调剂
  type: 'text' | 'number' | 'date' | 'boolean' | 'select' | 'multiSelect' | 'longText';
  group: string;              // 求职意向
  aliases: string[];
  options?: Array<{ key: string; label: string }>; // 通用选项定义，不是用户的选择
  version: number;
}

interface ProfileFieldValue {
  profileId: string;
  fieldId: string;
  value: unknown;             // 私人内容，仅本地保存
  source: 'user' | 'resume_import' | 'verified_existing_profile';
  updatedAt: string;
}

interface MappingRule {
  siteOrigin: string;         // 经校验的站点 origin
  fieldFingerprint: string;   // 脱敏字段特征
  fieldId: string;
  context?: { section?: string; repeatGroup?: string };
  confirmed: boolean;
  verifiedAt?: string;
}

interface FieldProposal {
  status: 'matched' | 'needs_confirmation' | 'missing_value' | 'suggest_new_definition';
  proposedDefinition?: FieldDefinition;
  suggestedFieldId?: string;
  evidence?: string[];        // 只引用允许展示的证据，不编造个人事实
  requiresUserApproval: true;
}
```

以上为**逻辑接口示例**；正式实现应对照阶段 2 的 Schema v3，避免发生不必要的破坏性迁移。多段教育、实习、工作和项目经历应保留独立记录 ID，而不是将所有经历压缩成单字符串。

## 4. 阶段 3｜AI 字段识别与本地学习（最高优先级）

### 4.1 开发任务

- **S3-01 字段扫描：** 识别 `input`、`textarea`、`select`、radio、checkbox、日期、可搜索下拉、动态添加的经历；提取可见标签、`name`、`placeholder`、ARIA、候选项、分组/重复组。对隐藏控件、验证码、密码和登录页执行排除规则。
- **S3-02 本地匹配：** 按「用户已确认映射 → 标准字段 ID / 同义词 → 上下文规则 → AI 待确认」排序。对本科/硕士/第一学历/最高学历必须识别重复组与层级，不允许仅凭包含“学校”就写入最高学历。
- **S3-03 AI 请求：** 用户主动选择后展示待发送字段元数据和服务商；通过扩展后台请求已有配置的模型；超时、401、429、无 Key、密钥未解锁均返回明确状态。
- **S3-04 AI 输出约束：** 严格 JSON Schema 校验；仅允许 `map_existing`、`propose_definition`、`needs_user_value` 等有限操作；禁止任意 HTML/JS 执行；对提示词注入和恶意字段文本做隔离。
- **S3-05 新字段创建：** AI 提议名称、ID、类型、分类、别名及通用选项；用户确认后先写**字段定义**。若有本地可靠内容，再另行显示值的来源及差异，确认后写**个人字段值**；没有依据时留空。
- **S3-06 用户补充与学习：** 允许用户在侧边栏输入缺失值，或明确选择“保存我刚刚在网页中填写的内容”；保存后可手动纠正；敏感字段需再次确认。
- **S3-07 映射记忆：** 仅在用户确认、并且填写结果验证成功后，保存网站映射；支持修改、撤销、禁用和删除；下次同类字段优先本地命中，不再消耗 AI Token。
- **S3-08 填写状态：** 显示 `matched`、`needs_confirmation`、`missing_value`、`filling`、`success`、`failed`、`unsupported`，并附错误原因。保留不自动提交、不处理验证码及密码的安全限制。
- **S3-09 Schema/备份兼容：** 与 Schema v3、多档案、现有 JSON 导入导出和已加密模型设置兼容；若确需升级，必须实现幂等迁移、回滚和版本化测试。

### 4.2 必须通过的验收场景

- [ ] 原有字段无需 AI 即可匹配；无网络时仍可填基本信息。
- [ ] 未知字段在用户授权后获得 Mock AI 的结构化建议。
- [ ] “第一学历毕业院校”正确关联本科记录，不误用最高学历。
- [ ] 本地已有可靠值时可以提出建议，但**修改或新增字段值前必须确认**。
- [ ] 本地没有信息时只创建空字段，不生成虚构答案。
- [ ] 用户确认的新字段与个人值分别保存；刷新和重启后仍存在。
- [ ] 同一字段再次出现时命中本地映射，不重复请求模型。
- [ ] 错误 JSON、429、超时、无 Key、锁定 Key、恶意网页提示均安全失败。
- [ ] 表单填写后能够回读校验；失败显示明确原因。
- [ ] 阶段 2 的 54 项基础测试和 31 项 E2E（或合理更新后的等效回归集）仍通过。

**阶段交付：** 扫描器/匹配器/建议器/映射存储的独立模块、最小确认界面、Mock AI、自动化报告、已知限制、更新的进度文档。

**退出条件：** 在可控模拟网站上，完整跑通「未知字段 → AI 建议 → 用户确认 → 保存 → 填写校验 → 再次匹配无需 AI」闭环；不要求此阶段完成最终 UI 设计。

## 5. 阶段 4｜现代化中文 UI / UX 重构

### 5.1 设计目标

采用简洁、清晰、适合 Edge/Chrome Side Panel 的工作台式布局。**功能优先、逐步替换 UI，不重写已稳定的领域逻辑**。建议 React + TypeScript 和可复用组件，现有模块通过统一服务接口调用。

### 5.2 信息架构

| 界面 | 功能重点 |
|---|---|
| 工作台 | 当前页面识别状态、资料完整度、近期填写、待处理字段 |
| 我的简历 | 多档案、多段经历、搜索编辑、导入与逐项核对 |
| 当前网申 | 一键扫描、匹配明细、按状态筛选、单项/批量填写、结果核验 |
| AI 字段识别 | 未知字段、模型建议、来源依据、用户确认与新增字段 |
| 字段库 | 标准字段、个人自定义字段、类别、别名、字段空值提示 |
| 映射记忆 | 站点映射、首次确认时间、成功记录、撤销和停用 |
| 数据管理 | JSON 导入、导出、差异预览、备份恢复、迁移状态 |
| 模型设置 | 服务商、Base URL、模型、Key 口令解锁、连接测试、请求范围 |
| 诊断中心 | 脱敏日志、扫描结果、失败原因、导出调试包 |
| 公共字段同步 | 阶段 6 再启用；先留入口或隐藏未完成功能 |

### 5.3 交互与视觉规范

- 核心操作“扫描当前页”“一键填写”“查看建议”在侧边栏 1–2 次点击内可达。
- 字段状态有**文字说明 + 图标/颜色**，不能仅靠颜色区分。
- 高风险操作明确展示**旧值 → 新值**，必须可取消；避免自动覆盖用户已填内容。
- 提供空状态、错误状态、加载状态、密钥锁定状态、网络断开状态及可恢复提示。
- 支持键盘导航、焦点样式、合理字号、窄窗口滚动、长字段折行和简体中文文案。
- 保留测试可识别的稳定 `data-testid`，避免测试强依赖 CSS class。
- 没有实现的功能不显示为可操作按钮；不要做仅有视觉效果的假入口。

### 5.4 验收要求

- [ ] 所有阶段 2–3 的能力可通过新 UI 完整操作。
- [ ] 侧边栏在窄宽度、浏览器缩放、中文长文本下无横向溢出和按钮遮挡。
- [ ] AI 请求授权、密钥锁定、字段差异和填写失败状态容易辨认。
- [ ] 原有备份、简历导入、加密 Key、动态字段功能无回归。
- [ ] Playwright 对主流程截图比对与交互回归通过。

**阶段交付：** 完整新 UI、组件及状态规范、截图、可访问性检查记录、更新的 E2E 测试。

## 6. 阶段 5｜北森 / Moka / 飞书等复杂网申适配

### 6.1 适配策略

采取**通用引擎 + 平台适配器 + 可回退手动处理**三层结构。检测到复杂控件后先识别其类型，再选择合适适配器；不允许 AI 直接执行网页脚本。

### 6.2 重点任务

- **S5-01 可搜索下拉：** 输入学校/专业名称、等待候选、检查选择项文本与内部值。
- **S5-02 日期控件：** 年/月/日、起止时间、至今、分离的年月选择器。
- **S5-03 重复记录：** 按真实页面结构增加本科、硕士、实习、项目；防止重复新增和跨记录填写。
- **S5-04 SPA 动态变化：** React/Vue 状态、异步渲染、导航跳转、重试和超时机制。
- **S5-05 自绘控件：** Ant Design、Element 风格选择器、按钮组、地区联动、表单校验。
- **S5-06 限制与保护：** 对跨域 iframe、closed Shadow DOM、复杂上传控件等无法安全操作的情况给出人工处理提示。
- **S5-07 站点诊断：** 生成不含个人字段值的控件摘要和失败原因，以便 Codex 修复适配器。

### 6.3 验收矩阵

| 场景 | 自动测试 | 人工验证 |
|---|---|---|
| 基础文本、单选、复选 | Playwright 模拟页面 | 真实页面抽检 |
| React/Vue 受控输入 | 组件状态断言 | 页面跳转后检查值仍存在 |
| 搜索式学校下拉 | 候选项 ID 与文本回读 | 至少一个实际平台 |
| 多学历/实习/项目 | 动态追加及顺序测试 | 检查真实网站分组映射 |
| 分步向导 | 每一步保存后重新扫描 | 前后步骤切换检查 |
| 复杂日期/至今 | 日期边界和校验测试 | 真实日期控件抽检 |
| 不支持控件 | 安全退出及提示测试 | 用户可手动继续 |

**验收标准：** 在模拟页面上完成可靠的真实交互；每个声称已适配的平台必须附测试日期、页面类型和截图/脱敏结果。**不把模拟测试通过宣传为真实平台全部兼容**。

## 7. 阶段 6｜GitHub 公共字段定义同步（不含内容）

### 7.1 唯一允许进入 GitHub 的数据

```json
{
  "id": "accept_relocation",
  "label": "是否接受工作地点调剂",
  "type": "boolean",
  "group": "求职意向",
  "aliases": ["是否接受全国调剂", "是否服从工作地点分配"],
  "version": 1
}
```

**禁止：** `value`、`answer`、`profileId`、任何真实个人经历、简历文本、API Key、token、身份信息、用户的选择结果、个人网站填写记录。网站专属 `MappingRule` 默认不属于公共字段同步范围。

即便只有字段名称，也可能夹带个人内容（例如网页标签混入姓名、手机号）；必须进行**字段级白名单构造 + 敏感信息扫描 + 人工审核**。不能仅通过删除名称为 `value` 的属性判定安全。

### 7.2 开发顺序

1. **本地学习：** 新字段先进入私人数据库的“待审核公共定义”，其中不包含值。
2. **去重与规范化：** 检查字段 ID 冲突、别名相似、类型不一致；拒绝不合法字段。
3. **安全导出：** 从 FieldDefinition 白名单重新构造 JSON，通过 Schema 和脱敏检查。
4. **差异预览：** 显示新建、更新、冲突字段；由用户确认。
5. **第一版同步：** 导出待提交的 `fields.json`，由本地 Git / Codex 检查并推送 `origin/main`。**不自动执行 push**。
6. **后续可选直接同步：** 经用户授权后使用 GitHub API。仅授予目标仓库 Contents 写权限；提交前重新读取文件 SHA，处理 409 冲突和权限失效；不得把令牌硬编码在源码中。
7. **下载合并：** 从 GitHub 拉取公开 JSON，校验字段 Schema 和版本，在本地增加新定义；**所有新字段的个人值默认空白**；任何仓库更新不得覆盖已有个人值。
8. **回滚：** 记录版本、合并差异、失败原因及本地回退点。

### 7.3 验收要求

- [ ] 上传内容仅包含允许的字段定义属性，无任何个人字段值。
- [ ] 含手机号码、邮箱、身份证号、真实简历段落的伪装字段被阻止上传。
- [ ] 相同字段多次同步不重复插入；冲突需要人工审核。
- [ ] GitHub 更新后新字段为空白；本地已有值原封不动。
- [ ] 断网、无授权、GitHub 401/403/409、格式错误时能回退且不丢数据。
- [ ] 公共字段同步与**个人完整 JSON 备份**是彼此独立的两个入口。

**阶段交付：** 公共 Schema、字段导出与审查器、双向合并器、同步界面、测试报告及 GitHub 权限说明。

## 9. 全程测试方案和调试方法

### 9.1 测试分层

| 层级 | 工具 / 方法 | 验证重点 |
|---|---|---|
| 静态与单元 | TypeScript、Lint、测试框架 | 字段 Schema、迁移、去重、脱敏、匹配规则 |
| API 集成 | 本地 Mock LLM | JSON 协议、401/429/超时、权限与安全边界 |

| 手工开发调试 | Edge/Chrome DevTools | Service Worker、Content Script、Storage、网络请求 |
| 真实环境抽检 | 受授权的真实招聘页面 | 真实站点兼容；只填表不自动投递 |

**注意：** 原仓库 `tools/verify.js` 会启动调试 Edge 并占用/清理指定本地端口；应在隔离测试环境使用，不能误杀其他开发任务。Playwright 扩展测试优先用其随附 Chromium 和独立用户目录，不与日常 Edge/Chrome 共用个人配置。

### 9.3 每次 Codex 修改的最小验证步骤

1. 运行项目中实际存在的**类型检查、单元测试、构建命令**；若脚本名称发生变化，以 `package.json` 为准，不猜测“已通过”。
2. 运行当前阶段相关 Playwright E2E；收集失败用例截图、控制台错误、服务工作线程日志和模拟 API 日志。
3. 运行全部旧功能回归；区分“真失败”和“旧版选择器已失效”。
4. 对涉及存储的修改执行“旧数据升级 → 写入 → 重启 → 导出 → 导入恢复”测试。
5. 对涉及 AI/GitHub 的修改检查 Network 请求体，禁止真实资料和密钥出现在测试报告中。
6. 更新 `DEVELOPMENT_PROGRESS.md`，记录通过/失败数量、命令、文件和未解问题。
7. 完成当前阶段后停止，等待用户验收；不自动跳到下一阶段，不自动推送 `origin/main`。

### 9.4 缺陷优先级

- **P0：** 泄漏密钥/简历、误投递、覆盖或丢失个人资料、公共仓库出现个人字段值。发现后停止发布并优先修复。
- **P1：** 核心填表链路不可用、错误字段被静默填写、数据库升级失败、授权逻辑错误。
- **P2：** 某些控件需手动处理、UI 不便、非核心兼容问题；明确记录替代操作。
- **P3：** 文字、布局和可选功能优化，不阻断核心测试。

## 10. 开发执行规则与 Git 工作流

1. 基于你自己的 Fork 仓库在本地开发，默认只使用 `origin/main`；**不要求添加 `upstream`，不另外创建长期开发分支**。
2. 每个阶段开始前读取 `DEVELOPMENT_PROGRESS.md`、Schema 文档、上一阶段测试结果和本计划；保持功能边界一致。
3. Codex 可以在本地实际编码、测试、修复；未经用户明确要求，不得 `git push`、创建 PR 或发布安装包。
4. 尽量按功能块小步提交。提交前检查 `git diff`、`git status`、`.gitignore` 和敏感文件，使用清晰提交信息。
5. 不允许通过删除测试用例、降低断言、改为假成功状态来“提高通过率”。
6. 真实站点测试与真实 API 测试应单独标记，不能用 Mock 的通过率替代。
7. 用户最终负责安装扩展、授权访问招聘页面、确认资料和点击投递。

**建议的提交粒度：** `feat(scanner): ...`、`feat(matching): ...`、`feat(ui): ...`、`test(e2e): ...`、`fix(storage): ...`、`docs(plan): ...`。
